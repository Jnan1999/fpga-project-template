# P0 需求捕获（Requirements Capture）

> 阶段目标：把领导的初步需求 + datasheet + 性能指标，转化为**量化、可验证、双方确认**的 SRS/RTM。
> 本阶段核心交互模式是**主动提问协议**——尽量把所有需求在前期锁定。

## 1. 入口条件
- 新项目目录已由初始化工具生成（或本模板已复制）
- `project.yaml` **一区已由用户填写**（项目名/器件/开发板/工具版本）；未填则提示用户先填
- 用户已提出初步需求描述；datasheet/BOM 等参考资料已上传至 `docs/refs/`（如有）

### 1a. 参考资料完备性检查（主动提问协议的第 0 步）
读完用户需求描述后，**先列出本设计依赖的器件/资料清单**（BOM 级：ADC、DDR、
光/电连接器、电源、时钟源，以及涉及的接口标准），逐项核对 `docs/refs/` 是否已有对应
datasheet/手册：
- **缺失 → 主动提醒用户上传**，并说明缺它会导致哪些需求无法量化（如"没有 ADC
  datasheet，采样时序与接口电平只能猜"）；
- 用户可选择**让 agent 联网检索**代替上传：检索到的 datasheet 必须**下载落盘到
  `docs/refs/` 并记录来源 URL 与版本/日期代码**（证据可复查，ADR 0012）；检索结果
  与用户上传件冲突时以用户上传件为准；
- 资料清单（器件 → datasheet 文件名 / 来源 / 版本日期）**附在确认清单第 10 节开头**，
  与该节"从 datasheet 推导的隐含需求"一一对应；**关键器件 datasheet 缺失时，
  依赖它的问题不得标 ✅**。

## 2. Agent 输入（必读）
> 以下清单为**最低要求**（下界非上界）；发现清单外相关资料须主动阅读并在汇报中注明（行为总纲 §6）。

| 输入 | 路径 |
| --- | --- |
| 项目基础信息 | `project.yaml` 一区 |
| 需求确认清单模板 | `docs/00_project/00-00_需求确认清单.md` |
| 参考资料（datasheet/BOM/标准） | `docs/refs/` 全部相关文件 |
| SRS/RTM/立项书模板 | `docs/00_project/00-01~00-03` |
| 器件资源总量（写资源指标时参考） | 按 `project.yaml` 的 part 查 Xilinx 手册 |

## 3. Agent 任务（主动提问协议，严格按序）

> **交互格式**（状态头/提问格式/阶段推进循环/状态持久化机制）见
> `docs/templates/_示例_P0交互流程.md`——协议管"做什么"，该文件管"每轮对话长什么样"。

1. **禁止直接写 SRS**。先综合三类输入（用户需求描述 + `docs/refs/` 资料 + 目录结构/project.yaml），生成 `docs/00_project/00-00_需求确认清单.md`：
   - 按模板 10 个类别列出**所有**待确认问题，每问给出【建议答案 + 依据】
   - **依据优先级**（用户 2026-10-16 明确）：① 用户上传手册（`docs/refs/`，引用到 文件名+章节/页码）→ ② 联网检索（须用户同意、落盘并标注来源）→ ③ 通用工程经验（只作建议，标"待手册核实"，不得写成事实）
   - 必须包含从 datasheet 推导的**隐含需求**（如"ADC datasheet 标注 DCO 最高 200MHz、t_SKEW=0.3ns，采样时钟方案选 BUFIO 还是 BUFR？"——注明 datasheet 页码/章节）
   - 模糊表述必须追问量化（如"采样率 100MSPS 是每通道还是合计？""精度 0.1% 是满量程还是读数？"）
2. **多轮对话逐条确认**：每轮回复开头输出状态头（阶段 + 清单 ✅/🔄/🔲 计数 + 资料状态）；用户回答后立即回填清单文件。
   清单全 ✅ 且三份草稿评审后，**由 agent 主动询问"是否进入下一阶段（P1 系统架构）"**——用户只做选择（"确定"或"我还想修改 XXX"）；每次修改完成后 agent 必须**重新主动询问**，沉默≠同意。
   用户确认"进入下一阶段"= 走 `/project:gate`（G1）申请流程，**不是直接跳到设计**——
   G1 之后是 P1 系统架构（模块划分/ICD/寄存器映射），代码设计从 P2/P3 才开始
3. 清单**全部 ✅** 后，才允许撰写三份草稿：
   - `00-01_项目立项书.md`（关键指标表必须全部量化）
   - `00-02_需求规格说明书_SRS.md`（每条需求可衡量、有验收口径；禁止"高速""低延迟"这类形容词）
   - `00-03_需求跟踪矩阵_RTM.md`（每条需求填验证方法：Simulation / Analysis / Inspection / Test）
4. 提示用户与领导确认最终版；用户确认后回填评审记录

## 4. 验证命令
本阶段无代码命令。完工自查项（`uv run python scripts/check_gate.py exit P0` 提供机读核对，人工项见 manual 清单）：
- [ ] `00-00_需求确认清单.md` 无 🔲/🔄 项
- [ ] SRS 每条需求含量化指标与验收口径
- [ ] RTM 每行"验证方法"列非空，且每条 SRS 需求在 RTM 有行
- [ ] 立项书"不做什么"一节非空

## 5. 出口标准（G1 spec review）
- 用户审核 SRS/RTM/立项书，并与领导确认通过
- 用户确认后更新 `project.yaml`：`P0.status: done`、`P1.status: in_progress`、`current_phase: P1`

## 6. 常见失败模式
| 失败模式 | 规避 |
| --- | --- |
| 假设需求、不提问直接写 SRS | 违反协议第 1 条，一律返工；先出确认清单 |
| 需求写成形容词（高速/低延迟/高精度） | 全部量化：数值 + 单位 + 测量方法 |
| 漏掉 datasheet 隐含约束（电平标准、时序参数、温度范围、初始化序列） | 逐页过 datasheet，约束全部进清单第 10 节 |
| RTM 只有需求没有验证方法 | P4 无法闭环；RTM 行必须含验证方法 |
| 修改 `project.yaml` 一区 | 一区只读；确需修改须用户显式指令 |

# workflow/ —— Agent 阶段操作规程

> 每个阶段一个 playbook。Agent 进入项目后：读 `project.yaml` 的 `current_phase` → 打开对应 playbook → 严格按其执行。
> 每个 playbook 固定 6 节：**入口条件 / Agent 输入 / Agent 任务 / 验证命令 / 出口标准(Gate) / 常见失败模式**。

## 阶段模型（V 模型 + UltraFast 方法论）

```
P0 需求捕获 ─G1→ P1 系统架构 ─G2→ P2 模块设计 ─接口冻结→ P3 并行实现 ─G3→ P4 功能验证 → P5 时序收敛 → P6 集成上板 ─G4→ Release
                                                              ├─ RTL 三件套（rtl-engineer）
                                                              ├─ Golden Model（golden-modeler）
                                                              └─ 验证环境（verification 骨架）
```

| Gate | 名称 | 机读判据 | 确认人 |
| --- | --- | --- | --- |
| G1 | spec review | 需求确认清单全部 ✅；SRS 每条需求量化可衡量；RTM 每行验证方法非空 | 用户 + 部门领导 |
| G2 | architecture review | 每个 SRS 功能需求有模块承接；每个接口在 ICD 有章节并登记 interfaces 表；每条 CDC 在 01-04 清单 | 用户 |
| — | 接口冻结（P2 出口） | `project.yaml` interfaces 全部 `frozen: true`；每模块 LLD 评审通过 | 用户 |
| G3 | pre-commitment review | `check_ports.py` 全模块退出码 0；elaboration 无 error；`report_methodology` 无 critical warning | 用户 |
| — | P4 出口 | 功能覆盖率 100% + 行覆盖率 ≥95% + 分支 ≥90%；全回归 PASS；RTM 验证状态回填 | 用户 |
| — | P5 出口 | post-route WNS ≥ 0；`report_methodology`/`report_drc` 无 critical；资源 < HLD 预算 | 用户 |
| G4 | release review | 板级用例全过；三路比对差异在量化误差内；Release 包（比特流嵌 git hash） | 用户 |

## 状态更新规则
1. Agent 完成某阶段全部任务 + 验证命令全绿 → 向用户出示结果，申请 gate 评审
2. 用户确认通过 → 更新 `project.yaml`：该阶段 `status: done`，下一阶段 `status: in_progress`，`current_phase` 前进
3. **Gate 未通过时禁止推进**；第二批的 `scripts/check_gate.py` 将对此机械强制

## 失效传播矩阵（评审#3 / ADR 0012）—— 上游变了，哪些已完成结果必须作废

> 仅有"推进规则"不够。某上游产物变更后，依赖它的旧证据**自动失效（stale）**，需重新评估。
> 状态取值扩展为：`pending / in_progress / gate_review / done / stale / blocked`。

| 变更对象 | 必须重新评估（至少） | 受影响状态 |
| --- | --- | --- |
| SRS / ICD / LLD | 受影响模块的设计、Golden Model、测试及相关评审 | 该模块 verified→stale |
| RTL / 参数 / IP 配置 | 功能回归、综合实现、相关板级证据 | P4→stale、P5→stale |
| XDC 约束 | 约束评审、时序结果、CDC 及相关板级测试 | P5→stale |
| TB / Golden Model / 覆盖率豁免 | 验证结论与覆盖率结论 | P4→stale |
| 工具版本 / 构建脚本 | 可复现性与全部受影响结果 | 全阶段重核 |

**证据绑定**：每份验证证据须记录 **源码/配置摘要(git hash) + 工具版本 + 测试集 + 种子 + 运行 ID + 结果 + 批准对象**。
**批准针对某次具体证据，不是笼统批准"P4 完成"**——证据失效则批准随之失效。

## 并行 Agent 写入所有权（评审扩展点 / ADR 0012）

P3 三线并行时，多个 Agent 可能同时触及共享文件。为避免互相覆盖：

| 文件/区域 | 写入者 | 规则 |
| --- | --- | --- |
| 各模块设计/模型/验证目录（`hw/rtl/<mod>`、`host/golden_model/<mod>.py`、`hw/verif/tb/<mod>`） | 对应线的子任务 | 只改自己负责的目录 |
| 共享索引（`project.yaml`、`rtl.f`、`verif.f`、测试矩阵、`contracts/interfaces.yaml`） | **协调者（主 Agent）统一合并** | 子任务不直接改共享索引，提交变更请求给协调者 |
| 验证证据（`logs/`、报告） | 由运行器（跑回归的进程）产生 | 不手工伪造 |
| 批准记录（gate、project.yaml 状态） | 仅经用户明确授权后更新 | Agent 不自行批准自己 |

## 运行产物按配置与批次隔离（评审扩展点）

保持 `impl_proj/`、`sim_proj/` 分离；为未来并行回归/调试版-发布版并存预留维度：
`目标板 / debug|release / run_id`。
每次运行至少记录：工具版本、参数、源文件清单、输入向量、种子、报告及输出摘要（对应 logs/README 的 SUMMARY 段）。
**两次并行回归、调试版与发布版构建，不得覆盖同一工程或让旧报告被当作新结果。**

## filelist 语法契约（评审#5② / ADR 0013）

`rtl.f` / `verif.f` 的输入格式约定（解析器实现归后续工具批）：
- **设计清单只含设计文件，验证清单只含验证文件**；命令行仿真需要总清单时另设聚合入口
- 注释单独成行；**禁止行尾注释**（会被当路径一部分）；路径相对仓库根
- `-f` 嵌套仅用于"验证清单引用设计清单"这一种；保持编译顺序、检测循环引用、校验设计集合与验证集合不交叉

## 人机分工总原则
| Agent 做 | 用户做 |
| --- | --- |
| 生成文档/代码/TB/Golden Model 草稿 | 审核、与领导对齐、理解计算流程 |
| 跑验证命令、读日志、分析失败、修 bug | 审核修复方案（diff） |
| 回填状态（测试矩阵/RTM/调试记录） | gate 确认、更新 project.yaml 阶段状态 |
| 列出决策选项 + 推荐 | 做最终决策 |

## 信任模型（ADR 0003，评审#1 修正）

> ⚠️ **检查核 ≠ 形式化证明核**。把端口检查/回归/覆盖率/DRC 类比 Lean kernel 有重要边界——
> 它们只证明"已执行用例通过"，**不能证明设计正确**。因此准确模型是三层：

```
LLM 生成 ──提议──▶ 分层证据检查 ──仍有共同盲区──▶ 独立评审 + 风险接受（人审 gate）
（不可信提议者）   （机器证据，非证明）            （只有这一层能盖章"可发布"）
```

**每项检查"能证明什么 / 不能证明什么"必须显式知晓：**

| 检查 | 能证明 | **不能**证明 |
| --- | --- | --- |
| check_ports | core/dft 端口名/方向/位宽一致 | 参数默认值相同、信号接对、功能正确 |
| 仿真回归 PASS | **已执行用例**通过 | 未测场景正确、期望本身正确 |
| 覆盖率达标 | 代码被执行的程度 | 期望结果正确、功能完备 |
| Golden Model 比对 | RTL 与 GM 一致 | GM 本身正确（两者可能继承同一份 LLD 的错误） |
| DRC / 时序通过 | 满足电气/时序约束 | 功能正确 |
| check_gate.py | 契约项被满足 | 契约本身正确、检查器自身无漏检 |

**由此派生的四条硬规则：**
1. 测试期望、覆盖率排除项、约束例外（false_path/multicycle）、检查器本身的修改 → **必须独立审核**（不能由产生它的同一 Agent 自审）
2. 检查器必须有自身测试，含**"故意引入错误必须失败"的反例**（fail-closed，见 ADR 0013）
3. 需求正确性、安全边界 **不因机器检查全绿而免于人审**
4. **不同 Agent 角色是分工，不自动等于独立验证**——独立性来自"依据不同来源推导"（如 GM 从 LLD 独立推导、禁止反向翻译 RTL），不是来自换了个 agent 名字

**按可信度分配 Agent 工作类型**（训练数据不对称：软件代码多而优，RTL 代码少而参差）：

| 任务类型 | LLM 可信度 | 策略 |
| --- | --- | --- |
| 阅读/分析（时序报告、日志、datasheet、波形） | 强 | Agent 主战场（P4 归因、P5 分析、P6 比对） |
| SV/UVM 验证代码 | 较强（接近软件） | 激进放手，Agent 大量生成 |
| RTL 生成 | 弱 | **组合大于创造**：复用 common/ 组件 + 官方 IP + 三件套模板，新造逻辑最小化，且每块新逻辑立即被验证闭包包住 |

架构优化总目标：**最大化"机器可产生有效证据"的工作量占比，并清楚知道证据的边界**；`common/` 组件 + 官方 IP + 上过板的模块构成可信积木库（类比 mathlib），随项目增多而增值。

## 契约两层（ADR 0001）
- **硬契约（围墙）**：出口机读判据 + 禁止事项——不可逾越
- **软契约（地板）**：各 playbook §2 的必读输入清单——是最低保障不是上限，鼓励 Agent 主动检索清单外资料并在汇报中注明

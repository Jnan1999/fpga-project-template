## 二、用户确立的核心设计思路（第一批最重要产出）

### 1. 人机分工：用户审、agent 执行
> "现在我开发 FPGA 项目的工作流程需要大量和 agent 交流""用户审、agent 执行"

agent 负责生成（文档/代码/TB/回归/修 bug），人在各阶段 gate 审核确认。架构一切设计服务于"让 agent 干的活可被机器快速验证，人只看必须由人判断的部分"。

### 2. 模板定位：骨架 + 占位符，供自研初始化工具生成空白项目
> "设计一个基础目录的骨架，后续使用 agent 开发项目……第一个初始化项目结构的工具，使用这个架构直接生成一个空白项目目录"

模板不是成品项目，是可复制的骨架。`<PROJECT_NAME>` 等占位符留给第五批的初始化工具替换。

### 3. 分批推进，逐批确认
> "每一批完成后也需要经过我确认才能进行下一批"

批次划分（ADR 0005）：①纯框架 → ②契约工具 → ③验证基础设施 → ④CI → ⑤初始化工具/插件。**当前在 ①收尾、②启动**。

### 4. P0 主动提问：前期尽量把所有需求定下来
> "一定要让 agent 主动提问，尽量把所有可能的需求都在前期确定下来"

P0 禁止假设需求：agent 依据用户需求 + datasheet + 目录结构发起多轮对话，生成需求确认清单，全确认后才写 SRS（`00-00_需求确认清单.md`，ADR 0006）。

### 5. 信任模型：RTL 创造不可信，阅读理解可信
> "不能完全相信大模型在 RTL 代码方面的创造能力……更应该相信大模型的阅读和理解能力"

训练数据不对称 → 按可信度分配任务：阅读/分析（强，agent 主战场）、SV/UVM（较强，放手）、RTL 生成（弱，**组合大于创造**：复用 common/ + 官方 IP + 三件套，新逻辑立即被验证闭包包住）。经评审修正为"分层证据检查，非形式化证明核"（ADR 0010）——每项检查能/不能证明什么必须显式知晓。

### 6. Xilinx 官方手册是一等输入
> "xilinx 的官方手册是最权威的参考资料……大量使用官方文档的参考示例或者官方 IP 与原语也能尽可能减少项目报错"

手册检索三层（ADR 0002）：手册地图（`docs/refs/xilinx/`）+ MCP（默认不启用，ADR 0007）+ 提示词引用规范（UG 号+章节+版本，禁止凭记忆编造数值）。**手册核实纪律**：无法查证时明确告知用户查哪本哪节，不得编造后标"待核实"。

### 7. 项目 = 边界清晰的闭包，类比 mathlib 复利
> "项目是一个拥有几乎完美边界的 closure 闭包……参考最近 AI 在数学上的极大进展"

需求/接口/测试/验证规则完整细分、边界清晰 → 可被机器检查兜住。common/ 组件 + 官方 IP + 上过板的模块 = 可信积木库（类比 mathlib），随项目增多而增值——这是模板长期复利的来源。

### 8. meta 元记录：每次调整带原因，ADR + devlog 双轨
> "把项目推送到远程仓库……记录 agent 开发过程，每次调整带原因"

模板/工作流/agent 的每次调整记 ADR（决策）+ devlog（动作），防设计意图丢失、决策反复推翻。模板级 ADR 在 `meta/decisions/`，项目级在 `docs/06_review/decisions/`（ADR 0015 分离）。

### 9. 三层职责 × 加载时机双轴
> "Agent 设计层 / 项目工作流程层 / 工具操作层"

职责三层正确，落地按 Claude Code 加载时机轴安放（ADR 0016）：总是加载=CLAUDE.md；路径懒加载=rules/；人触发=commands/；模型自动=skills/；阶段路由=workflow/；执行=工具脚本。横切数据面（project.yaml/contracts/docs/meta）不属于任一层。

### 10. 自由度理念（最新、最纠偏的一条）
> "我尽量少设计机械的执行步骤，而是尽量克制地介绍设计思路和大概的步骤，详细的执行我选择相信大模型的能力……现有的步骤规划对 agent 主要是参考"

这是对本批"过度工程化"的纠偏。**自由度分级**（ADR 0019，后续一切"要不要封装"的判断依据）：

| 级别 | 类型 | 处理方式 |
|---|---|---|
| ① | 顺序与禁忌（gate 顺序、frozen 接口、源文件外置） | CLAUDE.md 铁律（硬） |
| ② | 低频语法固定操作（建工程/仿真） | 示例脚本 + 机读契约，agent 自由改造，**不封装** |
| ③ | 复杂需方法论操作（时序收敛/CDC 审查/失败归因/覆盖率收敛/寄存器表） | skill 候选（第三批起） |
| ④ | 纯创意/分析（微架构权衡、调试根因） | 只给设计思路，完全放手 |

**机读契约是唯一贯穿所有级别的硬要求**：脚本末尾 `=== SUMMARY ===` 段，agent 只认它、缺失即 fail-closed。

## 三、第一批的纠偏记录（经验教训）

第一批经历了两次重要的"做减法"，值得后续批次警惕过度设计：

1. **评审纠偏（0010~0015）**：信任模型从"证明核"降为"证据检查"；三件套从铁律降为默认模式。
2. **自由度纠偏（0019）**：工具操作从"op 白名单 + 铁律 5 强制"降为"参考清单 + 机读契约唯一硬要求"，撤销铁律 5。

**共同教训**：能用"参考 + 信任 + 一个最小硬约束"解决的，不要上"强制 + 封装 + 白名单"。硬约束只留给"顺序、禁忌、机读判读"这三类。

# ADR 0020：方法自由、证据可追溯、验收不可自改（修正 0019 的"SUMMARY 唯一硬要求"）

- 日期：2026-10-16
- 状态：已确认（修正 [0019](0019_工具操作为参考非封装与不做MCP.md)；部分修订 [0018](0018_插件化打包边界.md)）

## 背景
外部模型对 0016~0019 的评审（2026-10-16）。核心批评：ADR 0019 把"执行方法可自由"正确放开，但把"判断成败只认 SUMMARY"当作唯一硬要求，**过强**——agent 可改写脚本，又只认 SUMMARY，则脚本可能漏测却输出 PASS、读旧报告打印格式正确的新摘要、或无意间放宽通过条件。评审主张核心原则应为"**方法自由、证据可追溯、验收不可自改**"，而非"SUMMARY 是唯一硬要求"。

同时评审指出多处需修正，本 ADR 一并裁决（采纳/拒绝）。

## 决策（核心原则）
**方法自由、证据可追溯、验收不可自改：**
1. **方法自由**：agent 可自由选择/改造执行方式（ops.yaml 是参考，非白名单）——保留 0019。
2. **证据可追溯**：每次正式运行必须能定位具体输入（git hash+参数+种子+run_id）与具体输出文件。SUMMARY 是**快速反馈格式**，由真实结果推导，本身**不构成 gate 证据**。
3. **验收不可自改**：agent 可改执行方法，但**未经审核不得改变验收含义**；gate 证据须核对"运行完成 + 输入身份 + 检查范围 + 原始报告 + 通过条件"。

## 补充（用户 clarifying 后的精确化）：SUMMARY 可信的两个前提 + tcl 两段分离

用户指出：agent 可改的 tcl 脚本主要是操作 Vivado 的"搬运工"，并不直接参与验证计划设计（验证计划/测试矩阵在 `hw/verif/` 与 `docs/03_verification/`），质疑评审"漏测却 PASS"是否成立。

**裁决：分层正确，但边界要划准。** "测什么、怎么判对错"确实由验证计划层保护；但 tcl 脚本（如 run_sim.tcl）恰好是**汇总各用例结果并打印 SUMMARY** 的那一层——它虽不管"测什么"，却管着"哪些结果被算进 PASS"。因此 SUMMARY 可信的前提是两点：

- **(a) 运行身份真实**：SUMMARY 由"本次 run_id 对应的真实、完整运行"产生（非旧报告、非未完成的后台任务）——由 run_id 绑定 + 完成/超时/取消三态保证；
- **(b) 判定口径未变**：产生 SUMMARY 的那段"汇总判 PASS"代码，其口径与已批准的验收标准一致——改动需经用户审核，与验证计划改动同级。

**由此落地 tcl 脚本两段分离：**

| 段 | 职责 | 修改自由度 |
| --- | --- | --- |
| 驱动段 | 建工程、启仿真、收集日志（搬运工） | agent 可自由改造（方法自由） |
| 汇总判读段 | 生成 SUMMARY、判定 PASS 的口径 | **属验收口径，改动需审核**——与验证计划同级 |

即：不是"tcl 是搬运工所以 SUMMARY 可信"，而是"tcl 里那一小段判读口径代码，属于验收标准的一部分"。评审说的"漏测却 PASS"措辞不准（漏测是验证计划层的事），但其真实风险成立——**验收口径可能被 tcl 层修改悄悄改变，而 SUMMARY 无法自证清白**。

## 理由
- "方法自由、验收严格"是本模板的正确姿态；但"严格"应落在**验收口径不可被自改 + 证据可追溯**，而非落在某一种反馈格式（SUMMARY）上
- run_id 绑定是防并行/过期证据串用的最小机制，不引入任务调度平台
- "检查权限不隐含修复权限"与"先设计后实现"是既有信任模型（0010）与阶段模型（0000）的自然推论，评审只是指出命令入口把它们绕过了
- 对无法证实的机制说法标"待验证"而非盲改，与本模板"禁止凭记忆编造"（0002）同一精神

# ADR 0005：批次划分——纯框架批先行，契约检查工具后置

- 日期：2026-10-15
- 状态：已确认

## 背景
最初计划第一批就含"可执行内容"（logs SUMMARY 的 tcl 实现等）。用户两次纠正定位：
1. "第一批主要是确定项目主体架构 + 指导 Agent 工作的 markdown 说明文件，而不是直接生成具体执行的 tool 或 skill"
2. "如果想让 Agent 每阶段完全遵守输入输出契约，可能还需要设计 check 工具或其他脚本代码"

## 决策
分五批推进，**每批完成需用户确认才进下一批**：
- 第一批（纯框架批）：markdown/yaml/配置，零可执行代码
- 第二批（契约工具批）：`scripts/check_gate.py` 契约检查器、`scripts/new_module.py`、tcl SUMMARY 实现
- 第三批（验证基建批）：`hw/verif/sv/` 骨架 + 分层回归 Makefile
- 第四批（CI 批）：ci/ 启用、寄存器表生成 C 头文件、干净 clone 重建 gate、golden-QoR 比对
- 第五批：初始化工具（用户自研）

其中 **`check_gate.py` 是核心**：读 project.yaml + playbook，机械验证入口条件/输入文件/产出清单/gate 机读判据，不达标阻止阶段推进。

## 理由
- markdown 契约是"文字"，没有强制力；check_gate.py 把契约从"靠自觉"变成"可强制执行"——它是信任模型（ADR 0003）kernel 的关键组件
- 先立框架再立工具，避免在规范未定前写死代码逻辑
- 分批 + 每批用户确认，符合用户"长期维护需真正理解、逐步审核"的诉求

## 后果
- 第一批 tcl 脚本的 SUMMARY 输出降级为"仅写 logs/README.md 约定文档"，实现后置到第二批
- check_gate.py 的设计直接由 playbook 的 6 节结构驱动（每节对应一类检查）

## 1. 仿真链路打通（run_sim.tcl 五轮实测收敛）

模板仿真链路此前从未真正跑通过。从首跑到 PASS 共五轮，每轮一个实证修复：

| 轮 | 失败现象 | 根因（实证依据） | 修复 |
| --- | --- | --- | --- |
| 1 | `axis_if.sv does not exist` | verif.f 引用整套未落盘的 UVM 式环境（与 batch 2 时 rtl.f 同病——"愿望清单"） | verif.f 裁剪到只含真实文件；新增真实自检 TB `tb_pulse_gen.sv` |
| 2 | `Spawn failed: Broken pipe`（compile 步） | 环境变量 `NoDefaultCurrentDirectoryInExePath=1`（本机用户环境已设置）使 cmd 不搜索当前目录；Vivado 以相对名 spawn 生成的 compile.bat → 子进程秒死 → 管道断裂。**手动验证**：同目录 `dir` 可见但裸名执行报"不是内部或外部命令"，全路径调用成功 | run_sim.tcl 驱动段首行 `unset -nocomplain env(NoDefaultCurrentDirectoryInExePath)`（仅进程内摘除，不动用户全局配置） |
| 3 | `Invalid coverage type 'sbc' ... allowed types: line branch condition or all` | 我按 xelab `--cc_type` 字母语法推错——Vivado 属性层取值是**单词** | `COVERAGE.TYPE = all` |
| 4 | `invalid command name "run_all"` | `run_all`/`close_sim` 是 **xsim** 命令，不是 Vivado 工程 tcl 命令；且发现 runtime=0 生成的 tb_pulse_gen.tcl 为 `run 0`——**仿真一步不走、日志无 FAIL、假 PASS（fail-open 陷阱）** | 移除 run_all/close_sim；`xsim.simulate.runtime = all`（生成 `run all`，仿真寿命归 TB 的 $finish） |
| 5 | — | — | **PASS**：`TEST PASSED: tb_pulse_gen all checks passed`，SUMMARY 契约完整（RESULT/RUN_ID/GIT_HASH/TOOL_VERSION/SIM_ERRORS） |

另含此前已修的覆盖率两处错：`-coverage all` 是新版语法（xelab 2021.1 无 `--coverage`
选项，`xelab --help` 实测 grep=0）；属性名 `xsim.elaborate.more_options` 在 2021.1
不存在（`list_property` 实测，正确名 `xsim.elaborate.xelab.more_options`）。

### 新增资产：tb_pulse_gen.sv（自检 TB 标准写法示例）

- 6 组自动比对检查：复位行为 / 脉冲间隔==cfg_period / 单拍脉宽 / 关断停脉冲 /
  cfg_period=0 保护 / 发布模式 wrap 调试输出 tie-off
- 自检口径遵守 tb-style 规范：失败打 `FAIL:`（run_sim.tcl 末尾扫描兜底，fail-closed）；
  期望来自模块功能定义（模块头注释），非 RTL 行为反推；带 200us 超时守护
- 单项失败打 `MISMATCH:`（刻意避开兜底扫描关键字，汇总由末尾统一判定）

### 教训（与 ADR 0020 更正同类）

- **"待核实"标注必须闭环**：`-coverage all` 的【待核实】挂了一个批次，实证后牵出
  连环三错（语法/属性名/取值格式）。评审质疑当时是对的。
- **runtime=0 是 fail-open 默认**：任何"仿真跑了但没有 FAIL"的证据都必须先证明
  "仿真真的执行了 TB"（如 TB 打印 TEST PASSED 且 SUMMARY 绑定 RUN_ID）。
- 环境变量问题（NoDefaultCurrentDirectoryInExePath）建议用户在系统环境变量中删除
  （影响所有 Vivado 仿真流程）；模板已内置进程级兼容，不依赖用户操作。

## 2. 常驻会话对照实验（MCP 核心假设先行证据）

**方法**：单 Vivado 进程内重复 5 次与 check_elab.tcl 完全相同的工作负载
（read_verilog rtl.f + synth_design -rtl），逐次记录 PASS/FAIL。
（实验脚本为非 op 一次性脚本，未入库；结果落 `FBG_32CH/logs/exp_persistent_elab_20261016_165439.log`）

**结果**：**5/5 PASS**（对照 batch 基线 4/5 失败 = 80%）。时间戳佐证机制：
第 1 次迭代 36s（进程内冷加载 Vivado 自身 rt 脚本——唯一的失败暴露窗口），
第 2-5 次迭代仅 6-9s（热态不再触碰启动路径）。

**结论**：间歇失败窗口在**进程冷启动**，常驻会话把 N 次暴露压缩为 1 次——
MCP（或任何常驻会话机制）在原理上可规避该类失败。局限：样本量小（5 次），
且本实验不区分"MCP 常驻"与"普通 tcl 常驻会话"（后者零新增组件即可实现，
代价是无 MCP 的结构化工具与跨客户端会话保持）。**ADR 0019 修订仍以用户在
FBG_32CH 会话中的 MCP 实测为准**，本实验为辅助证据。

## 3. 环境 flaky 事件簿（本机，2026-10-16）

| 事件 | 现象 | 归因 |
| --- | --- | --- |
| rt/*.tcl 读失败 | batch 4/5 失败，每次不同文件，重试即过 | 杀软扫描窗口（实测常驻会话 5/5 过） |
| sim_proj.sim 删除失败 | `Failed to remove the directory ... in use` | 瞬时占用（90s 后自行释放，rm 成功）；**另有一次是我自己的 shell cwd 坐在被删目录里**——Windows 锁定进程当前目录，后台命令删除前须确认主 shell 已离开 |

batch 模式失败率应直接下降；该建议与常驻会话方案不互斥。

## 4. 根因实锤与最终对照（同日，用户执行排除后）

**杀软不是 Defender 是火绒**：本机 WinDefend 服务处于停止状态，实际安装的是
火绒（Huorong，`E:\Huorong\`）。用户已将 `D:\XilinxTools` 与 `E:\Zynq7020`
加入火绒信任区，随即复测（与基线同协议：batch `check_elab.tcl` × 5）：

| 场景 | 结果 |
| --- | --- |
| 基线 batch（无排除） | 4/5 失败（80%） |
| 常驻会话（无排除） | 5/5 全过 |
| **batch + 火绒排除** | **5/5 全过** |

**结论**：间歇读文件失败 = 火绒实时扫描窗口，**环境修复可解**。ADR 0019 修订时
MCP/常驻会话的取舍权重相应变化：若 batch 失败率问题已被信任区解决，则"常驻会话"
的主要剩余价值是启动时间摊销与交互式调试，不再是可靠性——修订仍以用户在
FBG_32CH 会话的 MCP 实测为准（重点转向前者两个价值点的实测收益）。
另：`NoDefaultCurrentDirectoryInExePath` 经查为进程级注入（注册表用户级/系统级
均无此值），无持久化配置需删除；run_sim.tcl 已内置进程级兼容，闭环。
